# V60 · Portapapeles enriquecido y control del teclado

El usuario confirmó que V59 funciona con «Mostrar teclado virtual» desactivado, pero no con el ajuste activado. También informó de pérdida de subíndices/superíndices al pegar y de una demora visible al pasar a entrada física.

## Pegado

HiNote publica `text/html` además de texto plano y su formato privado. Importa HTML inerte a los segmentos del modelo: subíndices, superíndices, negrita, cursiva, subrayado, color, opacidad, tamaño, listas y saltos. No inserta nodos del portapapeles en el documento activo ni carga sus recursos. El formato propio sobrevive al recorrido Android que descarta el MIME privado.

Cuando WebView solo expone texto plano, el evento explícito de pegado puede consultar el HTML o Spanned del portapapeles nativo. Solo se utiliza si el texto nativo coincide con el texto de ese mismo evento. La lectura requiere foco de la app y nunca resuelve URIs. Si el origen únicamente proporcionó texto plano, se conserva el formato de destino; no se inventa formato ausente.

## Primera tecla y respuesta visual

La respuesta visual empieza en la primera pulsación mediante la API pública de animación del IME, cuando el sistema ofrece ese control. Solo modifica la presentación; no finaliza la composición ni reenvía la tecla. La política definitiva sigue esperando la edición nativa y liberación del evento. Se devuelve primero el control de la superficie y después se cambia la política nativa, para conservar visibles la barra compacta y las teclas al volver a Mostrar virtual. La animación también se cancela al cambiar de modo, volver al toque o perder foco. El sistema puede denegar o cancelar su control; no se promete latencia cero en todos los teclados.

## Control ampliado opcional

La API ordinaria de Accesibilidad no ofrece un control universal e independiente de teclas y candidatos. El usuario ya comprobó que su IME trabaja correctamente con la preferencia física desactivada. Esta prueba añade una ruta explícita de desarrollo que adapta temporalmente esa preferencia a dicho comportamiento y conserva el valor original.

Requiere ambos pasos voluntarios: preparar el control en Archivo → Control del teclado → Control ampliado, y conceder `android.permission.WRITE_SECURE_SETTINGS` mediante ADB. Instalar el APK no concede el permiso y el permiso solo, sin esa preparación, no activa la función. Los modos siguen siendo Automático / Mostrar virtual / Solo físico. No se añade un selector de marca.

El único ajuste seguro escrito por esta clase es `show_ime_with_hard_keyboard`. El valor original se registra antes de modificarlo, se restaura después de liberar nuestra política de Accesibilidad al salir/perder foco, y se recupera al iniciar si hubo una interrupción. Se respetan otras políticas y un cambio posterior detectado. Un cierre forzado del proceso puede aplazar la recuperación hasta el siguiente inicio; la ayuda lo indica antes de activar esta ruta.

Para esta versión independiente:

```sh
adb shell pm grant com.hinote.studio.keyboardtrial60 android.permission.WRITE_SECURE_SETTINGS
```

El servicio de Accesibilidad opcional se llama **HiNote · Control del teclado V60**. El APK usa `com.hinote.studio.keyboardtrial60`, versión `6.0-teclado-prueba`; no reemplaza los datos de V59 ni de Stable.

## Verificación

Las pruebas del editor incluyen el recorrido HTML sin MIME privado, formato mixto, pegado externo, listas, deshacer/rehacer, persistencia, carga inerte y rechazo de un portapapeles nativo que no coincide. Los tests de Android comprueban spans nativos, autorización/consentimiento y recuperación del ajuste.

La instrumentación usa Android 12, una tecla del kernel y un IME de ensayo que implementa la ventana compacta nativa cuando la preferencia real lo permite. Ese proveedor solicita la visibilidad de su superficie, como requiere Android 12; sus decisiones no leen el modo de HiNote. Se mantienen las aserciones de píxeles, texto único y contadores nativos. Los casos con control ampliado conceden el permiso explícitamente y verifican la concesión real del paquete. También se prueba la ruta estándar y que no modifique el ajuste activado sin consentimiento. Esto no equivale a ejecutar SwiftKey/Celia en HarmonyOS.

Verificación final: 246/246 pruebas del editor, incluidas las seis del portapapeles, y 118/118 de Python correctas. Las tres variantes Android completaron 360 pruebas unitarias sin fallos y dos omisiones condicionadas a la variante. El APK firmado contiene los 21 recursos web verificados contra sus fuentes y las clases nuevas de portapapeles y teclado; no incluye el IME de ensayo.

Comprueban texto original único, cierre visual desde la primera pulsación, candidatos visibles, Ctrl+1/2/3, reapertura de las teclas completas, solicitudes tardías, ajuste del sistema activado/desactivado y restauración al salir. El proveedor de ensayo acepta la visibilidad compacta aunque Android conserve SHOW_EXPLICIT de una solicitud anterior; la evaluación nativa de la vista mantiene cerradas sus teclas. Las aserciones siguen comprobando píxeles reales. Queda pendiente la prueba en HarmonyOS con SwiftKey/Celia.
